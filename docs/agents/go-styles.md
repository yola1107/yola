# Go 编码规范

适用于手写 Go 业务代码和测试代码。

## 重构与协议

- 简化或重构须保持行为不变。按改动范围核对随机调用的次数与顺序、金额精度、错误匹配、`nil` 与空集合的语义、锁范围和 I/O 时序。
- 协议字段、编号、JSON 标签和冻结样本保持原值，任务要求变更的除外。

## 命名与结构

- 命名简短且表意，沿用领域用词。省去上下文已有信息，保留必要区别。使用 MixedCaps 和 `ID`、`HTTP`、`RTP` 等惯用缩写，不生造缩写。
- 改名须同步受影响的引用，不为缩短名称批量改名。
- 包级未导出变量和常量（含哨兵错误）不强制加 `_` 前缀。
- 非空结构体声明展开为多行，每行一个字段。空结构体保留 `struct{}`，简短初始化允许单行。

## 函数与方法

- 优先标准库和具体类型。保留有助理解和组织代码的抽象，新增抽象须降低当前复杂度。
- 必需依赖显式传入。参数容易混淆时使用请求结构体。函数签名优先单行，过长影响可读性时再换行。
- 先处理错误和边界，用提前返回或 `continue` 减少嵌套。只抽取有独立职责的步骤，保持主流程直接。
- 同一类型的相关方法放在一起，组内先放主入口，再按调用顺序放辅助函数。局部修改保留无关函数的位置。
- 同一类型的接收者名称保持一致，通常也统一使用值或指针。方法需要修改接收者、类型含锁或复制成本高时用指针，可安全复制的小值类型可用值接收者。调整前核对 `T` 和 `*T` 的接口实现与编解码行为，契约需要时保留两种接收者。

## 校验与错误

- 在边界校验外部输入，内部沿用已验证的条件。金额、权限和并发状态按业务契约检查。
- 错误须处理或向上传递。包装时若需保留错误身份，用 `%w`。调用方用 `errors.Is` 匹配已知错误，用 `errors.As` 提取指定类型的错误。脱敏后仍须保留取消、超时和提交结果未知的语义。
- 提交、写入和影响完整性的清理错误必须处理。例如，`Close` 若会写出缓冲数据，就须检查它返回的错误。只有确认可安全忽略的清理错误才显式写 `_ =`。
- 日志按需在处理边界记录一次，不输出凭据、完整敏感请求或私有玩家资料。业务核心通过返回值或业务接口提供事实，日志与 tracing 放在边界和运行层。

## Context、并发与资源

- Context 以首参数 `ctx context.Context` 沿调用链传递。创建方负责确保取消函数被调用。显式返回或转交取消责任时，由接收方调用。
- 请求取消后仍须完成的清理，用 `context.WithoutCancel(ctx)` 保留 trace 等上下文值，再为清理设置超时。
- 后台任务由生命周期所有者管理，批量并发设置上限，收尾设超时。
- 失败和退出路径都须释放资源。停机时先停止接入并通知任务退出。若取消信号无法唤醒阻塞的 I/O，由资源所有者在停机时限内中断该 I/O。待任务退出后关闭其余依赖。
- 共享数据明确修改权与同步责任，保持锁序及跨实例协调契约。网络调用避免长期占用业务锁。

## 注释与生成

- 注释用中文说明契约、原因或单位。涉及资源所有权、清理责任、失败行为或生命周期时，须写明相应约定。
- 导出类型、构造函数和跨包入口须说明职责或契约，注释以声明名开头。简单构造函数若名称已说明用途且没有额外契约，可省略注释。例如，返回的资源须由调用方关闭时，就要写明关闭责任。
- 自解释字段和访问器无需重复说明。普通 `package`、`import` 声明无需注释。
- 生成代码只改输入并重新生成，保留生成标记。
